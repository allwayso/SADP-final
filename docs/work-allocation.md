# 四人分工说明

## 1. 分工原则与预计比例

按业务纵向分工，每人同时负责一个模块的页面、接口、数据及演示用例，避免简单地将成员分成前端、后端、数据库、文档，导致多人等待。四个模块属于同一应用，独立开发通过接口和测试数据实现，不以拆成独立服务为前提。

成员对应：A 林尚直、B 任思远、C 徐晨帆、D 周臣。各占 **25%** 为原计划工作量比例；最终实际贡献比例尚待团队确认，不能把预计比例直接当作实际贡献。

## 2. 模块职责和个人交付

| 成员 | 负责模块 | 实现内容 | 独立交付与验证 | 计划比例 |
| --- | --- | --- | --- | --- |
| A 林尚直 | M1 用户与应用入口 | 微信登录与绑定、账户/角色；公共布局、路由、登录态；前后端项目骨架、配置示例和运行说明 | 登录/角色接口；公共页面入口；应用可启动；用身份桩支持其他成员开发；整合最终运行说明 | 25% |
| B 任思远 | M2 POI 采集与地图 | 拍照定位、文件保存、分类描述、采集版本；地图分类查询、错误及进展展示、路线导航；OCR 辅助 | 手机完成一次采集；地图能查到 POI；提供版本读取和摘要写入服务；采集表单可被整改及现场任务复用 | 25% |
| C 徐晨帆 | M3 核验与异议处理 | 待检/通过/错误标识；整改与驳回；异议提交；第三方任务分配、现场结果和最终裁定 | 用 POI 和消息桩完成状态流转；接入 B 的采集能力后跑通完整闭环；核验界面和任务界面；整理整体演示步骤 | 25% |

A 的公共骨架工作与 B 的地图/OCR 接入、C 的流程协调、D 的消息接入共同平衡总体工作量；各人维护自己模块的接口说明和基本验证，不把文档与测试单独推给某一成员。

## 3. 接口交接与不越界约定

- **A → B/C/D**：统一用户标识、登录上下文和角色类型，提供 `currentUser`、`requireRole`、`listUsers`。各模块自己的业务对象权限仍由负责人实现。
- **B → C**：提供 `getRevision`、创建采集版本及 `setReviewSummary`。C 负责何时允许整改、派单及裁定；B 不另建一套核验状态机。地图展示以摘要为准，核验历史以 C 的记录为准。
- **D → B/C**：统一 `notify(type, target, reference, text)`；明确目标为用户或角色。B/C 不直接发布 RabbitMQ 消息，D 不决定错误处理结果。
- **B ↔ C 的页面复用**：B 提供通用采集表单，C 提供错误单/现场任务上下文与提交入口。整改与现场采集由 C 的服务校验后调用 B，避免双向服务依赖。
- **A 与所有成员**：只有登录、布局和分页等基础能力进入公共代码。业务数据表分别归模块所有，变更跨模块接口时先同步相关成员及本目录文档。

## 4. 并行开发与集成顺序

1. **先统一边界**：四人确认角色、标识、POI 版本、错误单状态和服务参数；由 A 建立工程骨架与启动方式。B/C/D 使用固定用户、POI 或消息桩开始页面与业务开发，无需等待真实第三方平台就绪。
2. **各自完成最小模块**：A 跑通登录；B 跑通采集和地图；C 用桩完成核验与异议流；D 完成通知和聊天。每个模块都能通过演示数据验证。
3. **按依赖集成**：先接入 A 的身份服务，再连接 B 的采集与 C 的核验，最后接入 D 的通知链路；D 可以提前独立开发中间件与聊天。桩替换为实际服务后，核对权限、版本和状态含义。
4. **共同走完整场景**：采集 → 新数据通知 → 核验错误 → 点发通知 → 更新或驳回 → 私聊 → 异议 → 第三方现场复核 → 最终通知和地图进展。再检查两个群聊、公告、微信及 OCR 接入。

各成员在自己的功能分支提交代码，经其他成员阅读后合入主分支。初始设计文档已作为主分支基础；实现中保持小步提交，不要求提前搭建复杂 CI 流水线。

## 5. 成果归属与演示安排

- 团队共交：架构“一图二表”、最终源代码及一套可重复执行的演示步骤。A 维护运行入口，B 提供采集/地图数据，C 串联演示场景，D 检查消息与群聊；演示人最终由团队指定一位。
- 每人自交：课程要求的每周进度小结，以及第四次作业相关个人成果。进度小结依据实际工作填写，本次架构阶段不预写尚未发生的工作。
- 个人贡献记录：记录提交、模块内容、联调及问题修复，结项时补入真实姓名、实际比例与说明。当前四等分用于计划，不代表已经完成实现。
