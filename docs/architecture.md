# check@collect 架构设计

## 1. 目标与范围

为采集者、核验者及第三方工作人员提供 POI 采集、核验、整改、异议处理和交流能力。采集者使用带摄像头和定位能力的移动设备，核验及后台操作也可在 Web 浏览器完成，系统经 Internet 访问。

当前阶段确定模块职责、交互方式和关键业务约定，不展开页面细节、完整字段设计或具体 SDK 调用。后续成果源码、系统演示及个人每周小结仍需在实现阶段完成。

业务角色为采集者、核验者和第三方工作人员；后台管理员负责角色配置与系统公告。第三方账号由后台预先配置，角色可以兼任，但同一异议的第三方处理人不能是当事双方。

## 2. 架构选择

采用 **B/S + 逻辑分层 + 模块化单体**。前端使用响应式 Web 页面，兼顾手机和桌面浏览器；后端按业务划分四个模块，放在一个应用进程中，模块之间通过公开服务接口调用。

建议实现组合为 Vue 前端、Spring Boot 后端、PostgreSQL 数据库和 RabbitMQ 消息中间件。此处确定技术方向，具体依赖版本在实现时统一。图片保存在服务端文件目录，数据库记录文件标识及元数据；初版无需独立对象存储。

逻辑上遵循“页面与交互 → 应用业务 → 数据访问”的分层，各模块内部保持这一结构。物理上部署为浏览器、应用服务器、数据库及消息中间件；初版后端、图片目录、数据库和 RabbitMQ 可以部署在同一台服务主机上，逻辑分层不要求每层独占服务器。

该方案便于复用登录、地图接入和消息能力，并能让四人按业务模块并行开发。当前不拆微服务，不增加服务发现、独立网关或通用工作流引擎；这些均不是完成本作业的前提。

## 4. 表一：组件职责与数据归属

| 编号/组件 | 职责与所属页面 | 拥有的数据 | 边界 |
| --- | --- | --- | --- |
| M1 用户与应用入口 | 微信登录、绑定微信号；账户及角色；公共布局、路由与登录态；基础运行配置 | 用户、微信绑定、用户角色 | 提供身份与角色查询；不实现采集、核验或聊天规则 |
| M2 POI 采集与地图 | 拍照及自动定位、分类与描述、上传/补采；OCR 辅助；分类地图查询、错误及进展展示、路线与导航入口 | POI、采集版本、照片元数据、POI 核验摘要 | 拥有地图/OCR 适配器；不判定错误是否成立，不处理聊天 |
| M3 核验与异议处理 | 待检列表、核验通过、标识错误、整改复核、驳回讨论入口、异议提交、第三方任务及最终裁定 | 核验记录、错误单、异议单、第三方任务与结论 | 决定流程与状态；通过 M2 接口关联采集版本和同步展示摘要 |
| M4 消息与交流 | 系统点发/按角色群发、通知列表；错误单相关私聊；采集者群和核验者群 | 会话、会话成员、聊天消息、系统通知、收件/已读及投递状态 | 拥有 RabbitMQ 接入；传递通知，不据消息内容决定业务状态 |
| PostgreSQL 与照片目录 | 持久化结构化数据及图片文件 | 按上述模块划分逻辑归属 | 共用数据库实例，各模块只通过自身数据访问代码写表；图片读写由 M2 管理 |
| RabbitMQ | 对系统通知提供异步投递 | 待投递的通知标识 | 一个应用消费队列即可；不为每个用户建立独立服务或队列 |
| 地图/微信/OCR 外部平台 | 地图显示、查询、路线及导航；微信授权；照片文字识别 | 平台侧数据及配置 | 通过适配接口接入；实现阶段申请所需账号与凭据 |

模块独立指职责、数据所有权和接口独立，不指四套独立部署的系统。共用数据库不等于允许任意跨模块访问表。

## 5. 表二：连接件与接口约定

以下为实现边界，方法名和路径可在编码前统一调整；不要求此阶段完成完整 OpenAPI 文件。

| 调用方 → 提供方 | 连接方式/接口 | 主要输入 → 输出/效果 |
| --- | --- | --- |
| 浏览器 → M1 | HTTPS `/api/auth/*`、`GET /api/me` | 微信授权结果或绑定请求 → 本地登录态、用户及角色；第三方角色不由用户自行申领 |
| 浏览器 → M2/M3 | HTTPS `POST /api/pois`、`POST /api/pois/{id}/revisions`（M2）；`POST /api/issues/{id}/revisions`（M3） | 新采集/无活动错误单的普通更新由 M2 接收；针对错误单的整改由 M3 接收并协调新版本与状态 |
| 浏览器 → M2 | HTTPS `GET /api/pois?category=&bbox=&progress=` | 类别、地图范围、进展 → POI 位置、错误标识与处理摘要；详情包含对应照片和版本 |
| M2 → 地图/OCR | 地图适配接口、`recognizeText(photoId)` | 目标位置/照片 → 地图、路线导航能力/文字识别建议；地图渲染 SDK 可由前端调用 |
| M2/M3/M4 → M1 | 进程内 `currentUser()`、`requireRole(role)`、`listUsers(role)` | 当前身份/角色条件 → 用户及角色信息，用于授权和收件人选择 |
| 浏览器 → M3 | HTTPS `/api/reviews`、`/api/issues`、`/api/disputes` | POI 版本、通过或错误说明、整改/驳回/异议动作 → 核验与处理状态 |
| 浏览器 → M3 | HTTPS `/api/field-tasks/{id}/result` | 现场采集版本、裁定、理由 → 最终结果；仅指定第三方人员可提交 |
| M3 → M2 | 进程内 `getRevision(id)`、`setReviewSummary(poiId, revisionId, summary)` | 指定采集版本/核验摘要 → 不可变版本内容/地图展示状态更新 |
| M2/M3 → M4 | 进程内 `notify(type, target, reference, text)` | 通知类型、用户或角色、业务关联 → 通知标识；M4 异步投递 |
| 浏览器 → M4 | HTTPS `/api/notifications`、`/api/conversations/*/messages` | 取消息、发消息、标记已读 → 持久化通知或聊天记录；初版定时拉取新消息 |
| M4 → RabbitMQ → M4 | 发布/消费通知标识 | 待投递通知 → 收件记录；成功后确认消费，重复投递不重复建立收件记录 |
| 各后端模块 → 自有数据 | 数据访问接口/事务；M2 另读写照片文件 | 业务数据 → 持久化结果；禁止从浏览器直连数据库 |

共同约定：时间由服务器生成；标识为不透明字符串；分页使用 `page/size`；请求身份从登录态取得，不相信前端传入的操作人；状态变更必须带所针对的采集版本。进程内服务与 HTTP 控制器分开，其他模块调用服务，无需绕回 HTTP。

同进程、同数据库下，M3 修改错误单并调用 M2 更新核验摘要时使用同一业务事务，避免地图进展与核验状态不一致。通知失败不撤销已经提交的采集或核验结果。

## 6. 关键业务约定与流程

### 6.1 采集、展示与导航

1. 用户完成登录，采集页面拍摄或选择照片，设备自动取得拍照位置，并携带定位时间、精度及坐标系标识提交；不设置手动输入位置来替代自动定位。
2. 定位失败时提示重试或授权，保留照片草稿，不能伪造位置或把缺少定位的数据当成完成采集。使用设备定位得到的是拍照位置，不声称自动识别了被拍对象的精确坐标。
3. M2 保存照片、分类、描述和位置。OCR 返回招牌文字或分类建议，由采集者确认；OCR 不可用时仍可人工填写分类与描述。
4. 新采集或整改版本进入待核验，M4 向核验者群发新数据通知。地图按类别显示 POI，结合 M3 同步的摘要展示错误和处理进展。
5. 用户选中 POI 后，通过地图平台查询路线或打开导航。M2 统一处理地图坐标系适配，保留原始坐标及其标识，禁止把不同坐标系直接混用。

照片、POI 与采集版本使用不同标识。修改位置、照片或描述产生新采集版本，历史版本保留；核验必须明确针对哪个版本，防止更新后的内容与旧错误说明混淆。

### 6.2 核验、整改与驳回

核验者查看指定版本，可标记通过；发现错误则建立错误单，关联 POI、版本、出错说明与核验者，保存后通知原采集者。初版同一 POI 同时只处理一张未关闭错误单，补充错误通过该单继续记录，减少并发流程。

采集者收到问题后，可以重新采集、更新或驳回：重新采集与更新都形成新版本并回到待复核；驳回必须说明理由，错误单进入“有异议”，不会直接变成“已解决”。双方可从错误单进入私聊；达成共识后，由核验者确认整改通过或撤回错误标识并关闭错误单。

主要错误单状态为：**待处理 → 待复核 → 已解决**；驳回后为 **有异议**，可经沟通返回待处理或关闭，也可进入第三方处理中。无错误数据的核验通过记录不要求先建立错误单。

### 6.3 第三方处理与最终结果

任何一方在沟通后仍无法达成共识，可提交异议。M3 从已配置的第三方工作人员中选择一名不同于当事双方的人员并分配现场任务，由 M4 点发任务通知。初版采用简单名单选择及后台调整，不实现复杂派单策略；无可用人员时保留待分配任务，并显示待分配进展。

第三方工作人员到现场重新采集、核验，复用 M2 的采集能力保存现场版本，再在 M3 提交最终结论与依据。任务可以认定原数据无误，也可以以现场采集的正确版本替换错误数据；两种情况都明确指定最终有效版本。最终裁定提交后，异议单与关联错误单关闭，地图显示最终进展，系统分别通知当事双方。

最终结论及历史处理记录保留，原采集者或核验者不能再次修改该次裁定。新发生的问题应另行建立后续记录，不能覆盖既有最终结果。

### 6.4 系统通知与聊天

- 系统公告可由有权限的后台用户发给全部采集者，例如暂停工作的通知；新数据待检通知发给全部核验者。
- 错误提交后点发采集者；异议任务点发指定第三方；最终结果点发争议双方。通知携带 POI/错误单/任务关联，点击后进入对应页面。
- 错误单私聊仅对当事双方开放并保留聊天历史。预建“采集者交流”和“核验者交流”两个群，成员按角色管理；同一用户具有两种角色时可以加入两个群。
- 聊天消息先持久化，可使用同一通知机制提醒收件方；浏览器初版定时拉取，业务不依赖用户持续在线，不要求实现即时音视频或复杂 IM 协议。

M4 将通知、接收目标及按创建时角色成员快照生成的收件记录先写入数据库，记录待投递状态，再将通知标识发送至 RabbitMQ；消费端按“通知标识 + 收件人”幂等确认收件并更新投递状态。角色群发以创建通知时的角色成员为接收范围，避免重试时改变收件人。数据库中的待投递通知可在失败后重试，重复投递不重复建立收件记录。这个简单机制用于避免中间件短暂不可用造成通知丢失，不引入额外事件平台；业务真实状态以 M2/M3 数据为准。

## 7. 四模块的数据边界与协作约束

建议实现目录为 `frontend/src/modules/{identity,poi,review,messaging}` 和 `backend/.../{identity,poi,review,messaging}`。每个模块拥有对应前端页面、后端控制器、服务和数据访问代码。

共享内容只包含登录上下文、标识/分页等基础类型和公共布局。业务接口中交换标识及 DTO，不传递可被其他模块直接保存的数据库实体；不建立包罗所有业务的公共工具模块。

M2 的提交服务支持 `NEW`、`CORRECTION`、`FIELD_CHECK` 三种提交用途。普通采集与整改由采集者执行；第三方现场采集须提供其已分配任务标识，由 M3 在任务服务中确认权限后调用 M2 保存版本，避免 M2 反向依赖 M3。整改同理由 M3 协调错误单状态和 M2 版本创建；页面可复用 M2 的采集表单。表二中的版本创建接口由对应入口进行身份及用途检查，不向普通用户开放任意第三方采集能力。

核心依赖保持单向：M2 → M1/M4，M3 → M1/M2/M4，M4 → M1。通用身份检查由 M1 提供给业务模块；M4 不回调业务模块执行状态迁移。这样四个模块可以用接口桩独立开发并按依赖顺序集成。

## 8. 需求覆盖与验收场景

1. **采集与补采**：用手机提交照片、自动定位、分类和描述，换一终端能看到记录；收到问题后可以提交新版本。
2. **核验与地图**：核验者保存错误说明，地图按类别查询并显示错误及进展；选中 POI 能使用路线/导航功能。
3. **异议闭环**：采集者驳回、双方私聊、提交异议、第三方现场采集并作最终裁定，双方均收到通知，地图进展同步。
4. **消息与群聊**：演示采集者公告群发、核验者任务群发、问题点发及两个角色群聊；用户离线后再登录仍能读取消息。
5. **平台集成**：演示微信登录/绑定、真实定位、地图与 OCR 适配入口。开发阶段可用桩数据解耦联调，但演示必须标注模拟部分，不能将未接入的平台宣称为已经完成。
6. **权限与失败处理**：不能查看无权访问的私聊或提交他人的第三方结论；拒绝定位时不提交缺失位置的记录；重复消息不产生重复收件记录。

课程思路对应：以 B/S 适应移动与 Web 使用；逻辑分层和稳定接口控制变更范围；以组件及连接件描述结构；在维护、扩展与部署开销之间折衷。初版优先完成上述场景，后续根据实际需要增加部署和性能优化。
