# check@collect 修复与补全方案

截至 2026-11-09，M1 已合入。以下是待实施方案，基于同一主干 `e6982ba` 和三个仍开放的 PR：B 的 #2 `e387ca8`、C 的 #3 `2ba413f`、D 的 #4 `3272a31`。F01–F11 对应[审查报告](pr-review-2026-11-09.md)，验收依据为[作业原文](../desc.txt)和[架构设计](architecture.md)。

交付目标是让四个独立账号在同一部署上完成一次真实采集、一次整改和一次第三方裁定。地图上的照片、核验进展和收件人看到的通知都能追溯到本次操作的 POI、版本、错误单或任务。

## 一、四人如何并行实施

| 负责人 | 可以立即开始 | 交给队友的内容 | 合入前的检查 |
| --- | --- | --- | --- |
| A · 工程与身份 | 从当前 main 建立集成分支，协调迁移编号、公共路由、同域 HTTPS 部署和四个账号，准备微信回调 | 可启动的共同基线、按角色分配的四个独立 userId、演示配置和启动命令 | 空库迁移、构建、登录/改密、停用、退出和角色校验通过 |
| B · POI 与地图 | 修复 POI 更新授权和版本摘要，抽出采集表单，接地图与 OCR | 真实版本读写服务、文件上传表单、分类枚举、照片读取入口、地图详情路由 | 真机采集后能读回照片、位置和版本，其他采集者不能修改 |
| C · 核验与异议 | 保留已有状态机测试，补现场证据约束和真实文件接收，按下文对接 B/D | 可处理真实版本的核验、整改、私聊入口、异议和裁定流程 | 同一错误单的地图摘要、会话成员、现场证据与最终有效版本一致 |
| D · 消息与交流 | 修正迁移编号，提供正式公告、通知和私聊服务，限制故障演练接口 | 用户点发、角色群发、按错误单建立私聊、消息关联跳转及 RabbitMQ 配置 | 真实 broker 成功收发，断线恢复能补投，重复消费不增加收件记录 |

**建议合入顺序。** A 先协调 B/D 修复 F01，再将三个模块原始实现合到同一集成分支。共同文件由 A 处理，保留全部上传、Flyway、微信和 RabbitMQ 配置，以及 B 的 POI 子路由、C 对采集者开放的错误单页、D 的消息页。B/C/D 随后基于该分支提交各自修复，跨模块适配由调用方维护。A 在最后一次完整验收通过后提集成 PR。保留 Vue、Spring Boot、PostgreSQL、RabbitMQ 和现有四模块边界。

**数据库。** 对干净安装采用 M1 的 V1、M2 的 V200、M3 的 V300、M4 的 V400，后续迁移按各自区段递增。已存在的 V2 有 POI 和消息两种含义。A 先读取 Flyway 历史中的脚本名与校验和。可丢弃的测试数据使用新库复测。需保留的数据先备份，在副本上迁入新建的标准结构，保留 UUID、外键、版本关系、照片目录和微信绑定，再核对记录数、照片读取与业务流程后切换。旧的内存桩编号不能推导为真实 POI，仅在有可核实映射时迁移相应历史记录。

## 二、B 与 C 共用的采集和版本规则

| 入口 | 谁可以执行 | 请求与结果 |
| --- | --- | --- |
| `POST /api/pois` | 采集者 | 上传照片及设备定位，创建 POI 和第一个有效版本，进展为待核验 |
| `POST /api/pois/{id}/revisions` | 原采集者，且该 POI 无活动错误单 | 提交预期当前版本和采集表单，生成待核验的新版本 |
| `POST /api/issues/{id}/revisions` | 错误单原采集者，且状态允许整改 | C 校验错误单、状态和预期版本，调用 B 保存新版本，并在同一事务内推进到待复核 |
| `POST /api/field-tasks/{id}/result` | 当前获派的第三方工作人员，且与双方不同 | 提交裁定、依据、预期版本及现场采集表单，保存现场证据并确定有效版本 |

1. **统一表单，解决 F04。** B 将采集页中拍照、定位、分类与描述抽成一个 Vue 组件。普通采集沿用现有 multipart 字段 `photos/category/name/description/lon/lat/crs/locatedAt/accuracyMeters`。C 的两个入口也使用 multipart，在同一请求中附上业务字段。C 从登录态读取操作人，从错误单或任务读取 POI 和任务归属。名称按 B 的规则必填、最长 120 字，分类提交 B 的枚举值，页面显示中文。每次拍摄或换图时重新取得定位并记录时间与精度，定位失败可重试并保留照片。桌面或手机查看版本时均从 B 的照片接口加载图片。新接口上线同时切换 C 页面和测试，原有桩模式保留为独立测试配置。
2. **接真实 POI 服务，解决 F02。** C 在 review 包实现 `PoiRevisionPort`，调用 B 的公开服务。B 提供按版本读取、按 POI 读当前有效版本、列出当前有效版本、创建整改/现场版本和更新摘要的方法。适配器转换 UUID、版本视图和状态，照片以真实照片标识集合返回。待检列表读取各 POI 当前有效版本，再应用 C 现有的未核验、非本人提交和无活动错误单过滤。B 拥有照片及版本表，C 拥有错误单和任务表。
3. **在数据库事务中保护普通更新，解决 F05、F06。** B 和 C 的更新操作均先通过 B 服务锁住同一 POI 行。B 检查创建人、预期版本，以及自己保存的核验摘要中是否有活动错误单。C 建单、整改、驳回和关闭错误单时，同事务维护摘要中的活动错误单标识。统一按 POI、错误单、任务的顺序取得需要的写锁，锁定后重查归属、状态和版本。归属不符返回 403，过期版本或活动错误单冲突返回 409。C 已校验的整改通过内部专用方法保存，普通更新入口不能指定现场任务或自行改变流程用途。
4. **区分最新提交和最终有效数据，解决 F08、F10。** 普通新版本生效时同步写入该版本的待核验摘要，地图查询按 POI 和有效版本匹配摘要。整改进入待复核。第三方两种裁定均须保存带照片和定位的 `FIELD_CHECK` 证据版本。保存证据时先保留原有效指针，若裁定原数据无误则继续使用争议中的原版本，若裁定替换则指向现场版本。C 在同一事务内关闭任务、异议和错误单，记录证据版本与最终版本并写入最终摘要。现场证据在两种情况下都可查看。事务回滚时清理本次新写入的文件。

## 三、B/C 与 D 共用的通知和会话规则

B 在 poi 包实现 `PoiNotifier`，C 在 review 包实现 `NotificationPort`，均调用 D 的 `MessagingService`。正式配置各装配一个真实实现。B 的通知依赖须能在启动时发现缺失。C 的两种桩仅供模块测试使用。D 按下表接收现有枚举，B/C 负责将自己的业务事件转换为收件人、关联标识、标题和正文，解决 F03。

| 业务动作 | M4 类型 | 收件人与关联 |
| --- | --- | --- |
| 普通新采集、普通更新 | NEW_DATA | 全部启用的核验者，关联 POI |
| 标记错误 | ISSUE_RAISED | 原采集者，关联 ISSUE |
| 整改、驳回、撤回驳回 | ISSUE_RESPONSE | 负责该单的核验者，关联 ISSUE |
| 复核退回、通过、撤回错误 | ISSUE_RESPONSE | 原采集者，关联 ISSUE |
| 提交异议 | DISPUTE_OPENED | 另一方当事人，关联 ISSUE |
| 现场任务分配、改派或无人可派 | FIELD_TASK | 获派工作人员，或无人可派时通知管理员，关联 TASK |
| 最终裁定 | FINAL_RESULT | 两名当事人各一份，关联 ISSUE |
| 管理员发布采集公告 | ANNOUNCEMENT | 全部启用的采集者 |

**投递。** D 复用已有通知表、收件人表和补投任务。业务事务先持久化待投递通知与收件人快照，提交后发布通知标识到 RabbitMQ。若进程在发布前退出，恢复后由补投任务扫描待投递记录。消费端按通知标识和收件人幂等确认。B 的普通采集产生待检群发，C 发起的整改和现场采集由 C 按业务动作通知，避免同一次提交在 B、C 重复触发。对外部 broker 不可用的验收同时检查业务已经保存、通知可补投和消费者确实收到了消息。

**错误单私聊与跳转，解决 F07、F09。** 建单时由 C 把真实 issueId、collectorId、reviewerId 交给 D 的 `openIssueConversation`。按 issueId 唯一建会话并保存两名成员，重试返回已有会话。C 的错误单详情返回 conversationId，页面打开 `/messages?conversation=<id>`，D 加载该会话并校验成员。两类角色群聊沿用 D 的角色成员规则。通知按关联对象跳转，POI 打开 `/poi/{id}`，ISSUE 打开 `/review?issue={id}`，TASK 打开 `/review?task={id}`。将 C 的 FIELD_TASK 关联统一映射为 TASK。多角色用户遵循同一链接，详情权限由后端决定。

**公告和调试权限，解决 F11。** D 增加正式公告写入入口及表单，管理员填写标题和正文，后端通过 `requireRole(ADMIN)` 授权。默认关闭 `MESSAGING_STUB_ENABLED`。开发时主动开启的故障、补投和模拟场景操作也需后端管理员授权。以普通账号验证调试关闭时接口不可用、开启时写操作返回 403，并验证管理员在关闭调试的情况下仍能发布正式公告。

## 四、平台接入和部署

| 项目 | 实施工作 | 完成证据 |
| --- | --- | --- |
| 地图与导航 · B | 使用团队可获得授权的地图服务接入底图、点标记和路线规划，以当前位置为起点、POI 为终点打开导航。保留 WGS84 原始值，按所选平台要求在适配器中转换显示坐标。用真实 POI 分类及 C 的摘要驱动筛选、错误标记和进展。 | 手机地图能筛出同类点，选点后得到实际路线和导航入口，裁定后点位与摘要一致 |
| OCR · B | 在 OcrAdapter 接入一个可用的文字识别 API，凭据放后端环境。将返回的文字展示给采集者确认，可据此建议分类。超时或识别失败时保留原图，允许人工完成分类与描述。 | 用一张有招牌的照片展示实际识别文字、人工确认和提交后的结果 |
| 微信 · A | 使用团队已有网站应用，在授权回调域部署同域 HTTPS，配置 AppID、后端密钥、回调 URI、前端公开地址及 Secure Cookie。每人先用自己的账号改密并绑定个人微信。 | 四个账号返回四个不同 userId，同一人扫码与手机密码登录得到相同 userId，重复绑定、停用及退出后的访问符合规则 |
| RabbitMQ · D | 启动 Compose 的 messaging profile，正式环境使用 rabbit 传输。按部署环境配置可连接的 broker 账号、权限及地址。B/C 合入后通过真实业务触发消息。 | 记录一次业务通知 ID 对应的发布、消费、收件人和投递状态，再验证中断、恢复补投及重复消费 |

A 维护一份可重现的演示配置示例和运行说明。演示时将两个 REVIEW 桩开关、消息调试和 review 模拟数据关闭，指定真实地图、OCR 与 RabbitMQ 实现。保留照片持久目录与数据库卷。实际密钥写入部署环境。B 在选定供应商并取得授权后补录所需的配置项、配额及坐标系，A 核对 HTTPS 站点可访问相机、定位和微信回调。

## 五、联合验收与作业提交

以下验收使用同一部署、独立登录会话和实际 POI 标识。A 记录部署提交号，C 串联演示，B/D 分别准备地图、照片与投递证据。

| 验收场景 | 必须观察到的结果 |
| --- | --- |
| 1. 空库启动与身份 | 唯一迁移顺序 V1、V200、V300、V400。前端构建与后端测试通过。四账号独立，微信与密码登录可对应到同一个人 |
| 2. 普通采集与更新 | 手机提交照片、自动定位和 OCR 结果。另一个终端能读到真实照片。核验者收到待检通知，核验通过后再更新，新版显示待核验 |
| 3. 标错与整改 | 核验者看图标错，原采集者收到通知并打开正确单据。提交真实补拍照片后，核验者复核通过，地图与错误单对应同一版本 |
| 4. 驳回、私聊、异议与裁定 | 当事双方在错误单私聊交换消息，提交异议后指定第三方收到任务。用两张不同的错误单分别演示两种裁定，两次均有现场证据。最终地图分别指向原有效版、现场替换版，双方均收到结果 |
| 5. 权限与并发 | 他人普通更新返回 403。活动错误单或过期版本的普通更新返回 409。并发标错与更新后版本和错误单一致。无关用户不能读私聊或提交裁定。缺照片/定位不能结案，已完成裁定不能重复修改 |
| 6. 公告、群聊、中间件 | 采集者收到公告，两个角色群聊可独立交流。普通用户无法影响全局投递。broker 停机期间业务可提交，恢复后补投并消费，同一通知重复消费后不增加收件人 |

将审查中确认错误行为的探针改成期望正确行为的回归断言。保留 C 原有 8 个流程测试的有效覆盖，按现场证据新规则更新相应用例，再补一组关闭桩、贯通真实 M2/M3/M4 的集成测试。平台验收使用真机、真实凭据与 broker 的运行记录。
