三个 PR 的技术方向符合既定的 B/S、逻辑分层和模块化单体架构，也都复用了 M1 的账号与角色服务；但当前版本**不能直接合并后作为完整作业交付**。存在数据库启动阻塞、真实服务接口未连接、照片契约不一致，以及权限和版本状态问题。

它们可以视为各模块的阶段性交付。修复公共文件冲突后，代码可以一起编译；这不代表真实采集、核验、通知、私聊和异议流程已经贯通。

## 2. 主要问题（按优先级）

P1 表示会阻塞集成、造成越权或破坏主要业务闭环；P2 表示会造成错误展示、流程缺口或交付环境问题。

### F01 · P1：M2 与 M4 重复使用 Flyway V2，合并后后端无法启动

**位置：** [M2 V2__poi.sql](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/resources/db/migration/V2__poi.sql#L1)、[M4 V2__messaging.sql](https://github.com/allwayso/SADP-final/blob/3272a31740e83ebaca0179059519d0858c8740fa/backend/src/main/resources/db/migration/V2__messaging.sql#L1)。

Flyway 按版本号识别迁移，两份文件的业务名称不同不能避免冲突。试合并后执行后端测试，实际出现 `Found more than one migration with version 2`，Spring 上下文无法启动。M3 的 `out-of-order: true` 不能解决同号迁移。

**建议：** 在各分支合入前统一编号，例如 M2 使用 `V200`、M3 使用现有 `V300`、M4 使用 `V400`。已经执行过旧 V2 的开发数据库需要制定迁移历史处理方式；本次临时改名只针对一次性测试库，不代表旧库可以直接照搬。

**负责人：** A 统一约定，B/D 修改各自迁移；C 确认迁移配置。

### F02 · P1：M3 的 POI 端口只有内存桩，无法读取 M2 的真实采集数据

**位置：** [PoiRevisionPort](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/backend/src/main/java/edu/sadp/checkcollect/review/port/PoiRevisionPort.java#L13)、[ReviewStubConfig](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/backend/src/main/java/edu/sadp/checkcollect/review/stub/ReviewStubConfig.java#L17)、[M2 PoiService](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/PoiService.java#L104)。

M3 依赖 `getRevision(String)`、`latestRevision`、`latestRevisions`、`createRevision(RevisionDraft)` 和自己的 `ReviewSummary`。M2 提供的是 UUID 参数、不同 DTO 及独立的整改/现场采集方法，没有实现该端口，也没有完整对应的最新版本查询服务。

保持默认开关时，真实 POI 写入 PostgreSQL，M3 核验的却是另一套内存 POI，地图摘要也只写入内存。关闭 `REVIEW_POI_STUB` 后，源码中没有其他端口 Bean 可以满足 `ReviewService` 的构造注入。

**复现：** 在合并副本通过真实 `/api/pois` 上传后，该版本没有出现在 `/api/reviews/pending`；容器中的该端口实现全部为内存桩。

**建议：** 在 M3 侧增加调用 M2 公共服务的适配器，补齐 M2 的版本查询服务，统一分类、标识和摘要映射，并验证事务中同步真实地图摘要。保留 M3 → M2 的单向依赖。

**负责人：** B/C 共同对齐，C 接入适配器。

### F03 · P1：M2、M3 的业务通知均未连接 M4

**位置：** [M2 PoiNotifier](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/PoiNotifier.java#L8)、[M3 NotificationPort](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/backend/src/main/java/edu/sadp/checkcollect/review/port/NotificationPort.java#L10)、[M4 MessagingService](https://github.com/allwayso/SADP-final/blob/3272a31740e83ebaca0179059519d0858c8740fa/backend/src/main/java/edu/sadp/checkcollect/messaging/MessagingService.java#L44)。

M2 使用 `PoiNotifier.notify(String, String, String, String)`，但三个 PR 中没有实现类。M3 的 `NotificationPort` 只有记录型桩；M4 提供 `notifyRole` / `notifyUser` 等另一组接口，没有接入上述两个端口。

通知类型也需映射：B 的 `POI_SUBMITTED` / `POI_REVISED`、C 的 `REVIEW_*` 字符串与 D 的 `NotificationKind` 枚举不同。不能直接通过枚举同名转换完成集成。

**复现：** 真实采集成功后，对应业务标识在 M4 的 `notifications` 表中没有通知；容器中 `PoiNotifier` 实现数量为 0，M3 的通知端口仍为记录桩。

**建议：** 提供两个薄适配器，统一事件类型、目标用户/角色和业务关联；在完整业务提交后投递，验证新数据群发、错误点发、派单和最终结果通知。适配器所属位置需保持模块单向依赖。

**负责人：** B/C/D 对齐；D 提供消息契约和映射，B/C 接入各自调用点。

### F04 · P1：整改和现场采集的照片、分类及表单契约不能直接接上 M2

**位置：** [M3 CollectionForm](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/frontend/src/modules/review/CollectionForm.vue#L21)、[M3 RevisionDraft](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/backend/src/main/java/edu/sadp/checkcollect/review/port/RevisionDraft.java#L10)、[M2 SubmitCommand](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/SubmitCommand.java#L11)。

M3 选图后仅创建 `photo-${crypto.randomUUID()}` 和浏览器预览，没有上传文件；提交的是 JSON 和任意字符串照片标识。M2 创建版本则要求真实的 `List<MultipartFile>`，没有“先上传照片再凭 photoId 创建版本”的服务，因此仅增加 Java 类型映射仍不足以接通。

同时，M3 使用“餐饮、零售”等中文分类，M2 使用 `HOUSE/SHOP/BUS_STOP/PARK/TREE/SCENIC/OTHER`；M3 名称可空且最长 200 字，M2 名称必填且最长 120 字。M3 的 `RevisionCard` 目前仅显示照片标识，也没有供核验者查看照片的图片。

**建议：** 复用 B 的采集表单和分类定义，使整改/现场结果入口能够接收真实文件并由 M3 校验业务上下文后调用 M2；或者明确定义临时照片上传及消费接口。统一名称校验，返回可读取的照片信息，并在核验页面显示实际照片。

**负责人：** B/C。

### F05 · P1：任意采集者可以更新他人的 POI

**位置：** [PoiService.submitCorrection](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/PoiService.java#L67)。

服务只检查当前用户具有 `COLLECTOR` 角色，没有检查该 POI 的创建人/采集归属。`appendRevision` 虽然读取并锁住包含 `createdBy` 的记录，但没有使用它授权。

**复现：** 用 member-a 创建 POI，用 member-b 调用该 POI 的 `/revisions`，接口返回 200，当前版本变成 member-b 提交的第 2 版。这违反账号独立和业务数据按登录用户归属的约定。

**建议：** 普通更新只允许业务约定中的原采集者执行；整改和第三方采集由 M3 根据错误单或任务授权后调用专用服务，不把“具有采集者角色”当作记录访问权限。

**负责人：** B。

### F06 · P1：活动错误单期间仍能绕过 M3 直接更新 POI

**位置：** [PoiController.revise](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/PoiController.java#L56)、[PoiService.appendRevision](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/PoiService.java#L158)。

架构约定有活动错误单时，整改必须经 `/api/issues/{id}/revisions` 进入 M3；但 M2 的公开更新入口无条件调用相同整改服务，不检查是否处于错误处理或第三方裁定中，也不要求期望版本。

**复现：** 为真实 POI 建立 `OPEN` 错误单后，直接调用 M2 更新接口仍返回 200。M2 的当前版本已变为新版本，M3 错误单中的 `current_revision_id` 仍是旧版，绕过了“待复核”的状态变化。

**建议：** 区分普通更新入口与 M3 内部整改入口；在不引入 M2 → M3 反向依赖的前提下，由协调服务或 M2 可维护的流程锁控制普通更新，并在事务内核对期望版本。

**负责人：** B/C；A 确认依赖边界。

### F07 · P1：真实错误单不会建立双方私聊

**位置：** [M3 建立错误单](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/backend/src/main/java/edu/sadp/checkcollect/review/ReviewService.java#L126)、[M4 私聊服务](https://github.com/allwayso/SADP-final/blob/3272a31740e83ebaca0179059519d0858c8740fa/backend/src/main/java/edu/sadp/checkcollect/messaging/MessagingService.java#L121)、[唯一现有调用点](https://github.com/allwayso/SADP-final/blob/3272a31740e83ebaca0179059519d0858c8740fa/backend/src/main/java/edu/sadp/checkcollect/messaging/MessagingStubController.java#L137)。

`openIssueConversation` 只在 D 的模拟场景中调用，M3 建立错误单或驳回时没有调用它，也没有对应会话端口。M3 的错误单页面没有实际进入聊天的按钮。即便通知适配完成，真实错误单仍不会自动变成可讨论的会话。

**建议：** M3 在建立真实错误单时通过明确的会话服务传入错误单标识及双方 userId，取得 conversationId；错误单页面和消息页面支持进入该会话。继续由 M4 校验会话成员，不让 M4 反查 M3 数据表。

**负责人：** C/D。

### F08 · P2：新版本会继承旧版本“核验通过”的地图摘要

**位置：** [appendRevision](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/PoiService.java#L164)、[摘要查询](https://github.com/allwayso/SADP-final/blob/e387ca81f6d96a63eec0a93af5d51a705e75b6e0/backend/src/main/java/edu/sadp/checkcollect/poi/PoiRepository.java#L23)。

更新 `current_revision_id` 时没有更新或作废旧摘要；查询摘要只按 poiId 关联，没有核对摘要针对的 revisionId。

**复现：** 版本 1 写入 `PASSED` 摘要后提交版本 2，详情返回 `revisionNo=2`，但 `review.progress` 仍为 `PASSED`。未核验的新内容被显示为已经通过。

**建议：** 在普通新版本产生时将展示进展同步为待核验，或明确根据摘要版本与当前版本的关系选择显示；针对错误单的整改仍由 M3 在同一事务内写入待复核摘要。

**负责人：** B/C。

### F09 · P2：通知关联类型与页面跳转不一致

**位置：** [NotificationList.referenceLink](https://github.com/allwayso/SADP-final/blob/3272a31740e83ebaca0179059519d0858c8740fa/frontend/src/modules/messaging/NotificationList.vue#L10)、[M3 NotificationReference](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/backend/src/main/java/edu/sadp/checkcollect/review/port/NotificationReference.java#L9)。

采集者的错误单通知跳到 `/poi?issue=...`，但 B 的 POI 列表没有处理该参数；实际错误单详情在 `/review?issue=...`，C 已允许采集者进入。POI 关联跳转使用的 `ref` / `poi` 参数也没有相应详情处理。C 的现场任务关联类型为 `FIELD_TASK`，D 的前端只识别 `TASK`，未经映射会跳回工作台。

**建议：** 统一关联类型和路由：POI 进入实际详情或待核验位置，错误单进入 `/review?issue=...`，现场任务进入 `/review?task=...`，并覆盖多角色账号。后端仍校验访问权限。

**负责人：** B/C/D。

### F10 · P2：第三方“原数据无误”可在没有现场采集证据时完成裁定

**位置：** [ReviewService.submitFieldResult](https://github.com/allwayso/SADP-final/blob/2ba413fb6c64ee6855a344e15c394aa2bb163179/backend/src/main/java/edu/sadp/checkcollect/review/ReviewService.java#L393)。

只有选择 `REPLACED` 才强制提交采集内容；选择 `ORIGINAL_CORRECT` 时，仅提交理由即可关闭异议，不要求现场照片或定位。原有集成测试也明确接受这种请求。作业原文要求第三方去现场重新采集、核验，需要保留可演示的现场证据。

另外，当选择原数据无误但同时附加现场版本时，M3 将旧版本标为 finalRevision，而 M2 的创建现场版本会推进 currentRevision；适配时必须明确“现场证据版本”和“最终有效版本”的区别，否则地图当前数据与裁定版本可能不同。这一点为源码推导，尚未通过真实 POI 适配器联调。

**建议：** 两种裁定都保存现场采集证据；允许保留原版本作为最终有效数据，但必须在 M2/M3 中一致表达有效版本。

**负责人：** C，B 配合版本接口。

### F11 · P2：默认开启的消息桩允许普通用户影响全局消息投递

**位置：** [MessagingStubController.fault](https://github.com/allwayso/SADP-final/blob/3272a31740e83ebaca0179059519d0858c8740fa/backend/src/main/java/edu/sadp/checkcollect/messaging/MessagingStubController.java#L88)、[默认配置](https://github.com/allwayso/SADP-final/blob/3272a31740e83ebaca0179059519d0858c8740fa/backend/src/main/resources/application.yml#L44)。

消息桩默认开启，故障注入、模拟公告和重试接口没有管理员角色限制。故障开关使用共享 BrokerSimulation，会影响全部业务通知。

**复现：** 普通 member-b 调用 `POST /api/messaging/stub/fault`，提交 `{"down":true}` 返回 200，`brokerAvailable=false`。复现完成后已恢复该开关。

**建议：** 调试接口要求管理员，并在正式演示配置中明确关闭；另外提供真正的管理员公告入口。当前关闭消息桩后，硬编码的模拟公告入口也会消失。

**负责人：** D。

## 3. 相互兼容性

| 组合/层面 | 判断 | 原因与处理 |
| --- | --- | --- |
| M1 ↔ B/C/D | 基本兼容 | 复用 IdentityService、UUID 用户身份、现有角色和 CSRF；业务记录权限仍需各模块实现 |
| M2 ↔ M3 | 尚未兼容 | POI 端口、DTO、分类、照片传输、普通更新与整改边界未对齐 |
| M2 ↔ M4 | 尚未连接 | PoiNotifier 没有实现，真实新数据不会触发通知 |
| M3 ↔ M4 | 尚未连接 | NotificationPort 仍为桩；通知类型、关联类型及错误单私聊没有适配 |
| 数据库 | 阻塞 | M2/M4 都是 V2；业务表名称未发现相互重名 |
| 公共前端与配置 | 需要人工合并 | 路由、配置、导航、样式和文档均有共同修改 |

按 `#2 → #3 → #4` 在隔离目录试合并：

- #2 + #3 冲突：`application.yml`、`docs/README.md`、`router.ts`、`style.css`。
- 再加入 #4 冲突：`application.yml`、`docs/README.md`、`App.vue`、`router.ts`。

这些公共文件冲突可以通过保留各模块新增内容解决。路由合并时须保留 B 的真实 POI 路由、C 的真实 ReviewView 及对采集者的访问、D 的 MessagesView；配置合并时须保留上传大小、照片目录、各平台参数、Flyway 和消息参数。

GitHub 显示每个 PR 单独相对当前 main 均为 `MERGEABLE`，不表示三个 PR 之间能够无冲突合并，也不证明它们的业务契约兼容。

| 作业要求 | 当前状态 | 尚需完成 |
